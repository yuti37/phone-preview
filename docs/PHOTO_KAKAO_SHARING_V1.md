# 照片與 KakaoTalk 分享 V1.1

## 本機可用功能

照片 App 分享及 KakaoTalk 聊天室的「＋ → 앨범」共用下列三組配對、相同確認與寫入流程，每組單次傳送。必須確認照片成功解碼、故事時間不早於照片時間，再由玩家明確確認。取消不寫入資料。

KKT 選擇器直接引用原有 25 張照片，隱藏未解鎖及故事時間未到的照片；不符合接收者白名單的縮圖停用並說明原因，已傳送配對標示 `전송 완료`。沒有檔案上傳，也不會自動選圖。關閉選單保留原本聊天室捲動位置；傳送成功則顯示新圖片並關閉選擇器。原主動發訊選項可從輸入欄或「＋」內的 `메시지 보내기` 繼續使用。

| 互動事件 ID | 照片 ID | 接收者 | 既有照片故事時間 |
| --- | --- | --- | --- |
| photo-share-v1:meal-minhyuk | photo-9376 | 玟赫 | 2026/10/21 19:58 |
| photo-share-v1:work-manager | photo-9370 | 經紀人 | 2026/10/23 15:05 |
| photo-share-v1:restaurant-shownu | photo-9333 | 賢佑 | 2026/10/21 20:41 |

這些時間是現有虛構故事設定，不是照片真實拍攝日期。傳送時間取既有故事時間與該聊天室最新有效訊息的較晚值，再加一秒；不讀取裝置日期來推進劇情。所有照片仍沿用原始資產與相簿分類。

## 已核准並啟用的回覆

以下為使用者核准的虛構文案，不引用私人聊天語料。三組 `replyApproved` 均為 true，只在玩家新確認分享時建立對應回覆事件。舊存檔沒有分享事件，或舊分享未配置回覆時，不會追溯補發。

### 玟赫：舊餐點照片

- 韓文：이거 보니까 또 배고프네 ㅋㅋ 맛있었어?
- 繁中：看到這個又餓了ㅋㅋ 好吃嗎？
- 確認分享後延遲 3 秒送達；故事時間為分享後一分鐘。不假設這是當天剛吃的餐點。

### 經紀人：工作側拍

- 韓文：사진 확인했어요. 기록용으로 보관해 둘게요.
- 繁中：照片確認了，我會留作紀錄。
- 確認分享後延遲 3 秒送達；不新增工作安排、場次或任務。

### 賢佑：共同餐廳經歷

- 韓文：그날 잘 먹었지 ㅋㅋ 사진 보니까 생각나네.
- 繁中：那天吃得挺好的ㅋㅋ 看到照片就想起來了。
- 賢佑主線進行中仍可傳送。是否產生這句獨立回覆，依下節的傳送當下狀態決定；不推進感情或跨 App 劇情。

## 賢佑的固定回覆決策

成功傳送時，依固定優先順序決定並保存 `photoResponseMode`：

1. 正在與賢佑通話：`none`。
2. 有主線 pendingReply、飲酒待送回覆、初始主線 reply-pending，或已排程的賢佑主線訊息：`absorbed`。
3. 飲酒階段等待玩家選擇、等待隔天、其他正在等待玩家回答的多回合話題，或已有開場電話排程等明確衝突：`none`。
4. 無上述衝突：`direct`。

`absorbed` 及 `none` 只加入照片，不建立獨立照片回覆，不新增接收者已讀資訊，也不改動主線 pendingReply。之後重新整理或主線結束不會改判或補發。

`direct` 使用原核准文案，約 3 秒後送達、故事時間為照片後一分鐘。若等待期間啟動新通話、主線回覆或其他衝突，或聊天室故事時間已超過該回覆，事件永久改為 `inapplicable`，保留照片及當初的 direct 決策，不在衝突結束後恢復。新 direct 事件另有「預定送達後 30 秒」的傳輸有效期；超過此期才重載則失效。這只是延遲回覆的傳輸期限，不會改變遊戲日期或推進隔天。

玟赫與經紀人的原有回覆及暫緩機制保持不變。

## 資料及恢復

- 圖片訊息沿用原有 KakaoTalk schema，加入 `type: photo`、`photoId`、`sourceEventId`。舊文字訊息不變。
- 在既有事件儲存庫加入獨立的 `photoSharesV1` 版本化區塊，沒有新增儲存鍵。紀錄與訊息事件以同一次儲存寫入；失敗則還原記憶體，不顯示成功。
- 單次配對由穩定事件、訊息及紀錄 ID 三重去重。舊存檔缺欄位視為空；損壞或未知版本不覆寫。
- 已送照片透過既有完成事件重播機制重建，保留原本訊息去重、排序與已讀機制，不寫入主線對話事實。
- 回覆快照與排程共用既有事件資格檢查，不占用主線 pendingReply。賢佑採上述失效規則，其他接收者仍採 V1 暫緩規則。
- 三組正式回覆各自建立單次事件，故事時間為分享後一分鐘；重載使用已保存的回覆快照。自動化測試同時涵蓋正式文案及隔離的人工快照資料。
- 原有重新開始機制會一併移除事件庫內分享狀態，不碰其他儲存鍵。

新紀錄保存 `source`（photos 或 kakao-plus）、`photoResponseMode`、`responseDecisionAt`（故事時間）、`responseReason`、`responseEventId` 與必要的時間資訊。兩種入口另依 photoId + chatId 檢查舊紀錄及已送訊息，避免更換入口或舊情境別名繞過去重。

## V1 存檔相容處理

V1 原有紀錄包含 playerMessageId、replyApproved、replyEventId 與回覆快照。完成照片及回覆以相同 ID 恢復；不重寫已送達的內容。

| 舊資料 | V1.1 行為 |
| --- | --- |
| 沒有分享，或已分享但未配置回覆 | 不新增任何回覆 |
| 回覆已完成或已取消 | 保留原狀，不重播或重新排程 |
| 缺少模式、已有有效待送回覆 | 根據已保存的核准及事件 ID 讀取為 legacy direct；不寫入新模式，不更換快照、時間或套用新的 30 秒期限。仍須通過執行前的情境檢查 |
| 賢佑回覆在 V1 已是 deferred | 保留照片及事件，將該待送事件標記失效，避免很久之後補發 |
| 新版 absorbed / none | 保留原決策，永不因重載或主線結束新增回覆 |

無批次重建、沒有新增儲存鍵，所有處理都在玩家選擇繼續後才由原有恢復／資格檢查執行。

## 開發測試

- 自動化：`node --test tests/*.test.js`（Windows 可先列出測試檔再傳入）。
- 選用瀏覽器測試：`node tests/photo-kakao-sharing.browser.cjs`，開發環境需提供 Playwright，必要時由 `CHROME_EXECUTABLE` 指定 Chromium。測試只建立臨時無持久化的瀏覽器 context 與本機靜態伺服器。
- 瀏覽器測試檢查 320、390、430px；不等同真實 iPhone Safari 驗收。
